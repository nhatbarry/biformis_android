# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

"Biformis" — a Unity 2D top-down action game (working title `GameNameJamProject`, package `com.DefaultCompany.GameNameJamProject`). This branch (`GameName_Jam`) is the Android port of a PC-first game. Unity **6000.3.10f1**, URP 2D, New Input System only (`activeInputHandler: 1`).

To play in the editor, open `Assets/Scenes/CaptainPinkTurd/Bootstrap Scenes/Core.unity` and press Play (`Assets/Read Me.txt`'s "Scenes/Main" is outdated). `Core` holds the managers (Game, Sound, Music, Audio, Surface, ObjectPool, SceneController, DataPersistence) and loads the menu; a level run without Core auto-generates those singletons without their configuration and floods the console with NullReferenceExceptions (e.g. `SurfaceManager.HandleImpact` on every bullet hit) that aren't real bugs. To test a single level, just open it (any `Level…` or story scene) and press Play: `Story System/Editor/PlayOpenedLevelThroughCore` starts from Core instead and the menu jumps into that scene (toggle: menu Biformis > Play Opened Level Through Core; verified with this project's disabled domain/scene reload). The main menu also has a "Level select" button (a dev/demo tool, third in the button column; `StoryMenu` builds it at runtime and moves the column up to fit, uncheck `showLevelSelect` on it for a release build) to start the story at any step.

## Architecture

### Assembly layout

Code is split into ~20 asmdefs under `Assets/_Scripts/CaptainPinkTurd/<System Name>/`, one per gameplay system (Core, Input System, Animation System, Effect System, Spawn System, RPG System, UI, Units System, Score System, Scene Architecture System, Mobile Controls System, etc.), plus vendored third-party code under `Assets/_Scripts/PathCreator/`, `Assets/_Scripts/Unity-Bullet-Hell/`, and `Assets/_Scripts/xNode-master/`. Third-party assets are unmodified except where noted in `ANDROID_PORT.md`.

Per `Assets/Read Me.txt`, the codebase intentionally uses **heavy coupling between systems** (system A directly references system B) as a deliberate simplicity choice for a small team/game-jam scope — this is not an oversight, don't "fix" it by adding abstraction layers.

Each system that needs input reads it via its **own** `new InputSystemActions()` instance rather than a shared `PlayerInput` component — this is a foundational architectural fact that shaped how mobile input had to be implemented (see below).

### Mobile controls port (read `ANDROID_PORT.md` before touching input/UI/timescale code)

`ANDROID_PORT.md` (in Vietnamese) is a comprehensive, load-bearing design record for this branch: it documents the port's design decisions, every PC bug this port fixed, mistakes made and reverted, and traps for anyone touching PC code afterward. Read it fully before changing anything touching input, HUD/UI, `Time.timeScale`, camera framing, or sorting layers — it explains *why*, not just *what*.

Key points to internalize:

- **Core principle:** touch emulates a virtual Gamepad via Unity's `OnScreenControl`, injecting into control paths gameplay code already binds to (e.g. `<Gamepad>/leftStick`, `<Gamepad>/leftStickPress`, `<Gamepad>/rightShoulder`, `<Gamepad>/buttonEast`). No gameplay branch exists for mobile vs. PC — touch takes the exact same code path as keyboard input. Since input is per-system (no shared `PlayerInput`), device-level emulation was the only option that didn't require touching every system's action-reading code.
- Control-path-to-action mapping constants live in `Assets/_Scripts/CaptainPinkTurd/Core/Input Paths/MobileControlPaths.cs`. Adding any new keybind on PC requires also wiring a mobile button: bind an unused Gamepad control, add a constant there, add a `BuildButton(...)` call in `MobileControlsHUD.Build()`. `ANDROID_PORT.md` §7 lists exactly which Gamepad controls are free vs. already claimed — check it before reusing one.
- The mobile HUD (`Assets/_Scripts/CaptainPinkTurd/Mobile Controls System/`) is built **entirely at runtime in code** — no prefabs, no imported sprites, no scene edits — specifically to keep scene/build-settings diffs at zero.
- `MobileControlsHUD.IsGameplaySceneLoaded()` gates HUD visibility on scene names starting with `"Level"` — renaming that convention silently breaks HUD visibility.
- Several latent PC bugs were found and fixed while porting (detailed in `ANDROID_PORT.md` §5): a `Time.timeScale` restore bug in `HitStop`/`ShakeUtils` that could freeze the game permanently after a popup set timescale to 0, a `Renderer2D.asset` sorting-layer-texture bug that only manifested on Vulkan/GLES, an animation direction bug from comparing floats exactly against joystick input, and a `Timer` leak from `AnimationControllerBase.PlayAnimation()` not disposing its previous timer. Do not reintroduce any of these patterns (see the two rules below).
- **`Time.timeScale` rule:** never write `float old = Time.timeScale; Time.timeScale = 0; ...; Time.timeScale = old;` — if timescale is already 0 when this runs (e.g. during hit-stop), it freezes the game forever. Always restore via `Time.timeScale > 0f ? Time.timeScale : 1f`, and if restoring from an async callback (DOTween), use `OnKill` not `OnComplete` so it still fires when the tween is cancelled.
- **Float-equality rule:** never compare analog input (joystick) to cardinal vectors with `!=`/`==`; keyboard composites happen to produce exact `(1,0)`-style vectors so this bug hides on PC and only appears with analog input. Use nearest-direction-by-dot-product instead.
- To check whether a prefab is actually placed in a scene, grep the **prefab's GUID**, not the script's GUID — a prefab instance in a scene only stores an override reference to the prefab GUID, not the script GUID (a past investigative mistake, documented in §6).
- Full-screen UI overlays must use anchor stretch `(0,0)-(1,1)` with zero offsets, never a fixed size — a fixed `640x360` size only happens to cover 16:9 and leaves gaps on other aspect ratios.
- `CameraFraming.cs` (`Assets/_Scripts/CaptainPinkTurd/Core/Rendering/`) fixes world-space horizontal width across aspect ratios via `orthographicSize = min(authored, authored * (16/9) / aspect)`, applied directly to `Camera.orthographicSize` in `LateUpdate` with `[DefaultExecutionOrder(10000)]` — it deliberately does not depend on Cinemachine's `LensSettings.Orthographic`, which reports stale values on scene load. It spawns itself (`RuntimeInitializeOnLoadMethod`), so nothing in a scene references it — it was once deleted by accident in a dialogue-system commit and 20:9 phones showed empty background bands past the map on both sides; `CameraFramingTests` now fails if it's missing.
- `m_CameraSortingLayersTextureBound` in `Renderer2D.asset` (the renderer Android's Medium quality level uses) is a sorting layer **unique ID**, not an index: it must be the ID of the layer right below `CameraSortingLayer`, i.e. `Default` = `0`. It was once `8` ("Default is the 8th layer"), which matches no layer, so URP never captured `_CameraSortingLayerTexture` and the enemy-death screen shockwave smeared stale frames across the screen on phones. `RenderingSettingsTests` checks every renderer in use.

### Story mode (Vietnamese/English)

A story mode sits beside Endless (main menu "Cốt truyện / Story"; Endless is untouched).

- **Running order** is `Assets/Game Data/Story/Story Data.asset` (`StoryData`): cutscene steps name an ink knot, level steps name a scene. `StoryFlow` (`Scene Architecture System/Story/`) loads each step and **saves immediately** — `DataPersistenceManager` reloads the save file on every scene load, so an unsaved change is reverted by the very transition it triggers. `LevelManager.isStoryLevel` makes a level advance the story and restart itself on death.
- **Scenes** live in `Assets/Scenes/CaptainPinkTurd/Story/`: `Level Story 1–5` and `Level Story Corridor` (names start with `Level` so the mobile HUD shows), one shared `Story Cutscene` scene for every cutscene, and `Story Ending` (built entirely in code by `EndingSequence`).
- **Ink**: `Assets/Ink Dialogue/Biformis_Story.ink` (vi) and `Biformis_Story_EN.ink` (en) must keep identical knots, variables and tags. Tags stage the cutscene (`CutsceneStage`): `#speaker:`, `#bg:name|RRGGBB[:seconds]`, `#cast:`, `#fx:`, `#sfx:`, `#anim:Actor:clip[:delaySeconds]`, `#move:Actor:x[,y][:seconds]`, `#struggle:Actor:count`, `#flip:Actor:on|off`, `#fade:RRGGBB|in[:seconds]`, `#banging:Door:on|off`, `#knock:Door:level`, `#attach:Prop:Actor:dx,dy|none`, `#reach:Walker:Target:maxX`, `#alpha:Actor:opacity[:seconds]`, `#shake:units[:seconds]` (the comment block at the top of `Biformis_Story.ink` documents each); `#wait:seconds` and `#hold` are handled by `DialogueManager` itself (`#hold` waits until the stage calls `ReleaseStageHold()`, and continue input during staging is forwarded as `OnStageInput`; a full-screen `Stage Tap` on the stage canvas takes the taps while the panel is hidden): the tags before it run, the panel hides (`OnStagePause`) and input is ignored (`IsStaging`) while the stage acts, then the rest run and the line shows — use it for wordless moments (the first white room opens and closes this way). The dialogue panel (Story Dialogue System prefab) follows the team's reference: 608×108 `#212739` panel, text size 32 with line spacing −8 (the GIFs' 13 px lines per 16 px of font, so a three-line text clears the panel's bottom), a 168×168 portrait frame at its bottom left for every speaker that has one, and per-speaker name colours — all driven by `DialogueSpeakerStyle`, whose portrait clips are named after the `#speaker` value (`Villain_appear` → `Villain`, which idles and glints; no talking mouth, the villain's portrait shakes while its line types; a `<Speaker>_talk` clip plays while that speaker's line types — A's portrait is the team's `A_Portrait`, idle + talk, recoloured to A's mint). Name colours follow the team's latest READMEs (B `F14E52`, A `95E0CC` — A's mint, not the READMEs' blue —, villain `C8A07A`, Mom `F2C456`, doctor `95E0CC`, the pink teen `F6A09C`); B keeps the in-game portrait although the GIFs show none (the user asked for every character's face in the panel); every merged GIF line still fits three lines with it. Stage actors are drawn at 4 canvas units per art pixel on a floor at y −56 and kept right of x −124 so the portrait frame never hides them; nobody is dimmed while listening. The villain's red screen tint only applies when the villain has no body on stage. Cutscene art drawn in Aseprite is imported straight from the `.aseprite` file (`Assets/Animations/Story/`, Animated Sprite + Merge Frame, pivot on the canvas centre) and played by `StageActorAnimation`, whose clips are the file's tags with their frame durations copied into the Inspector — re-enter them if the timing changes in Aseprite. The first white room (`WhiteRoom_1`) is built from the team's files in `Assets/Animations/Story/`: `B_Bed` (B waking in bed, speaks as `B` via `StageActor.speakerId`), `Teen` (the teenager is A: its idle frames are Blue Character's pixels, its vanish recoloured to A) and `Villain` (plague doctor, walks to the bed and stabs B) plus `Villain_Portrait`. It closes on `Level3` (`Assets/Sprites/Story/Next Scene - Level Story 3.png`, Level Story 3 around the player's start rendered at one art pixel per pixel, 224×90, shown ×4) with `B_Floor` waking on that floor, then B's last line, then Level 3 starts on the same spot. `MC_WakeUp_Floor.aseprite` was assembled from Red Character's own idle pixels (lying = rotated) plus the bed file's FX, recoloured light for the dark floor — the team has no lying-on-the-floor drawing yet. On phones a cutscene is advanced only by tapping: `DialogueTapToContinue` is a full-screen raycast target behind the panel, so the panel's own graphics (back panel, text, continue icon, portrait frame) must keep `raycastTarget` off, and `DialoguePanelUI` may only switch its `GraphicRaycaster` off on a line with choices (it once did so after every line, which froze cutscenes on touch screens from the first line on). `DialogueManager` also auto-advances a line that has finished typing after `autoAdvanceBaseDelay` + `autoAdvancePerCharacter` × its length (2.5 s + 0.05 s/char, rich-text and `[speed=]` tags not counted), never while staging or on a line with choices. The team writes each cutscene's final dialogue in its preview GIF: when a GIF is given, its lines are used verbatim (same words, same grouping into lines — the opening's GIF merges three pairs of villain lines and has no "System starting up" lines); keep the English file's lines grouped the same way. In Level 4 A arrives already hurt: `PlayerSpriteSwap` in `Level Story 4` swaps the player's `Blue` renderer to `A_Bloody`'s sprite of the same name every frame (same frames, tags and sprite numbering as Blue Character; its hair recoloured to A's mint and outlined), so the player prefab and its animations stay untouched. `DialogueManager.ExitDialogue()` calls `story.ResetState()`, so visit counts don't survive between dialogues — use ink `VAR`s for anything that must.
- **Localization**: `Assets/Resources/Localization/Strings.txt` (tab-separated `key / vi / en`, must stay `.txt` — Unity doesn't import `.tsv` as a TextAsset), read by `Localization` + `LocalizedText` in `Core/Localization/`. Speaker display names are keys `speaker.<#speaker value>`. Menu/popup labels are TMP text on `UI Button Blank.png`; the old sprites had English baked in. The game font is `m3x6 VI SDF` (the original m3x6 plus 134 Vietnamese letters drawn by the team; static atlas sampled at 16 = 16 px/em with Point filtering, so every font pixel is a crisp square and existing font sizes stay as tuned for m3x6); `VT323 SDF` is only the TMP global fallback for characters m3x6 lacks.
- **Colour-coded gameplay objects** (static colour barriers, sliding walls) use `Sprite-Unlit-Default` so red/blue read correctly under each level's coloured lighting.
- The story levels' tilemaps were painted by an editor script. If you ever edit tilemaps from a script (especially in `-batchmode`), call `TilemapCollider2D.ProcessTilemapChanges()` and `CompositeCollider2D.GenerateGeometry()` before saving: the `Collision` composite (outline geometry) serializes its baked shape, and without a regeneration it keeps the old walls — this happened once and let the player walk through every wall.
- Level design constraint: the player's wall-blocking collider is a 0.75 × 1.175-cell box (`Player Sprite Collider`, layer `Player Collider`, excludes Red/Blue); the small hitbox circle is what colour barriers stop. A passage only 1 cell tall can't be walked through sideways.
- **Enemies & fights**: story levels have no hand-placed enemies. Each room is an `EncounterSpawner` (Story System): entering its trigger starts N waves of M enemies at the room's precomputed floor spawn points, and clearing them opens that room's gate (`Gate <n>` tilemap) or, for `Encounter Door`, the level's door. Per-wave counts are 2/3/4/5/6 for Levels 1–5 (turrets / Reaper / Axion+turrets / Riven / everything).
- **Luneblade enemies** (`Prefabs/Enemies/Luneblade/`, art by Jesshiyoo, sheets in `Sprites/Enemies/Luneblade/`): `LunebladeEnemy : BiformisEmitterController`, so they share health, colour cycling, alert icons, scoring and VFX with the turrets/spiders. Chaser (Reaper) runs in and slashes, Bruiser (Axion) closes to mid range and fires its current-colour emitter on the smash frame, Blinker (Riven) vanishes and lunges. Their own hits follow the bullet rule (only a player of the other colour, never a dashing one). They're animated from sprite frames (no Animator), have a dynamic Rigidbody2D + solid feet circle so walls stop them, and their emitters have `burstFire` off because they fire manually. They are also in Endless via `Enemy Loot Drop Profile`.
- Player colours map to the characters: Red = B (the brother), Blue = A. Level 4 locks the player to Blue via `DimensionLock` → `GameManager.LockDimension`.
